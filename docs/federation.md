# Систем холбох

Өөрийн системээ [sso.dgov.mn](https://sso.dgov.mn)-ээр нэвтрүүлэх.

Онцгой протокол, тусгай SDK байхгүй. Стандарт OpenID Connect —
`authorization_code` + PKCE. Ямар ч хэл дээрх ямар ч OIDC клиентийн сан
ажиллана.

## 1. Discovery

```
https://sso.dgov.mn/.well-known/openid-configuration
```

Энэ баримт бүх хаягийг зарлана: `authorization_endpoint`, `token_endpoint`,
`jwks_uri`, `end_session_endpoint`. Тэдгээрийг гараар бичих шаардлагагүй —
клиентийн сан discovery-г уншина.

`issuer` нь яг `https://sso.dgov.mn`. Токен шалгахдаа үүнийг тулгана.

## 2. Клиент бүртгүүлэх

Бүртгэлийг провайдер дээрх **SSO клиентүүд** дэлгэцээс, эсвэл API-аар:

```
POST /api/v1/sso-clients/apps
```

Өгөх зүйлс:

| Талбар | Утга |
| --- | --- |
| `client_name` | Системийн нэр — хүн уншина |
| `client_uri` | Системийн хаяг |
| `client_type` | `confidential` (сервер) эсвэл `public` (SPA, мобайл) |
| `redirect_uris` | Callback хаяг, яг таг |
| `post_logout_redirect_uris` | Гарсны дараа буцах хаяг |
| `grant_types` | Ихэвчлэн `authorization_code` |
| `scopes` | Ихэвчлэн `openid profile email` |

Гурван зүйлийг урьдчилан мэдэж байх нь зүйтэй:

**`client_id`-г та сонгохгүй.** Провайдер өөрөө гаргана — `app_` + нэрний
slug + санамсаргүй найм. Хүсэлтэд бичсэн нэр биш, хариунд ирсэн утгыг
тохиргоондоо хийнэ.

**Нууц нэг л удаа уншигдана.** Үүсгэсэн хариунд `client_secret` ирнэ; сан
нь зөвхөн digest хадгалдаг тул дахин харах арга байхгүй. Алдвал
`rotate-secret`.

**Public клиентэд нууц олгогдохгүй.** Мобайл апп эсвэл хөтчийн дотор
байгаа нууц бол татаж авсан хүн бүрийн уншиж чадах нууц. Тэнд PKCE
дангаараа барина.

## 3. Redirect хостоо бүртгүүлэх

Таны системийн хост нь провайдерийн `OAUTH_REDIRECT_HOSTS` жагсаалтад **яг
таг** байх ёстой. Тэр жагсаалт дэд домэйныг өвлүүлдэггүй:
`dgov.mn` бүртгэлтэй байх нь `alba.dgov.mn`-ыг зөвшөөрөхгүй.

Энэ нь давхардсан шалгалт: `redirect_uris` аль хэдийн яг тааралддаг. Хоёр
дахь нь буруу бүртгэгдсэн клиент нэг хүний алдаанаас бус, хоёр хүний
алдаанаас л гарч ирдэг болгож байгаа хэрэг.

## 4. Урсгал

```
таны систем  →  /oauth2/auth      (PKCE challenge, state, nonce)
sso.dgov.mn  →  нэвтрэлт          (eID / ДАН / нууц үг)
sso.dgov.mn  →  зөвшөөрлийн дэлгэц
sso.dgov.mn  →  таны callback     (?code=…&state=…)
таны систем  →  /oauth2/token     (code + verifier + client secret)
```

Токенийг `jwks_uri` дээрх түлхүүрээр шалгана. Түлхүүр эргэлддэг тул түүнийг
хатуу бичихгүй — `kid`-ээр нь discovery-гоос авна.

## 5. Хүн нь хэн бэ

Токен доторх `sub` нь тухайн хүний тогтвортой танигч. И-мэйл өөрчлөгдөж
болно, `sub` өөрчлөгдөхгүй — өөрийн талын холбоосыг `sub` дээр барина.

Провайдер танисан ч таны системд бүртгэлгүй хүнийг яах вэ гэдэг нь таны
шийдвэр: татгалзах эсвэл тодорхой байгууллагад автоматаар үүсгэх.

## Gerege Nexus дээр суурилсан систем бол

Тохиргоо л хийнэ, код бичихгүй:

```bash
SSO_CLIENT_ISSUER=https://sso.dgov.mn
SSO_CLIENT_ID=<провайдерийн гаргасан id>
SSO_CLIENT_SECRET=<үүсгэх үед нэг удаа ирсэн нууц>
SSO_CLIENT_TENANT=<танихгүй хүнийг ямар байгууллагад үүсгэх>
SSO_CLIENT_LOCAL_LOGIN=false
```

`SSO_CLIENT_LOCAL_LOGIN=false` болгохоосоо **өмнө** урсгалыг бүтнээр нь
гүйлгэж үзнэ. Тэрийг хийлгүй унтраах нь өөрийгөө хаах товч дардагтай адил:
буруу тохиргоо нь эхний хүн нэвтрэхийг оролдох хүртэл чимээгүй байна.

Тэр мөр нь дараа нь провайдер унасан үеийн буцах зам болж үлдэнэ —
`true` болгоод backend-ээ дахин асаахад дотоод нэвтрэлт эргэж ажиллана.
